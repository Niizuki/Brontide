## "Take the highest-priority item" does not say whether blocked counts

Date: 2026-07-31
Trigger: a rule I could not apply without guessing what it meant

`AGENTS.md` says to inspect `docs/future/README.md` before beginning planned implementation work and
"take the highest-priority item unless the user directs otherwise". The highest-priority item is
Priority 1, Portable Component Binding, whose two remaining steps are fresh independent reviews and
owner question closure — both of which that document explicitly records as *not the implementer's to
close*. Taken literally the rule selects work an implementing agent cannot perform, and taken
loosely it selects nothing in particular.

The priority document does resolve it, but only in the first sentence of Priority 2, which says
Component Management is "the next implementable programme while Portable Binding awaits reviewer and
owner actions". So the answer exists and is one level of indirection away from the rule that sends
you looking.

Conclusion: a priority-order rule needs to say what it does about an item that is blocked on someone
other than the reader. Either the rule says "highest-priority item you can actually advance, and say
which one you skipped and why", or the priority document is required to mark blocked items so the
ordering is directly readable. The failure mode is quiet rather than loud — an agent picks the
implementable item, which is right, without ever recording that it departed from the literal
instruction.

## The "property that cannot fail" rule caught a vacuous assertion

Date: 2026-07-31
Trigger: a rule that caught something I can name

Writing CBI17's shared-vector test, I asserted that the admissions and grants in force were
identical before and after a succession, to evidence the contract's claim that succession performs
nothing. Re-reading the ground rule that a property which cannot fail is a review finding against
the property, I checked whether the assertion could fail, and it could not: both stacks hold those
values in immutable records, so no implementation of the operation could have moved them, in either
language. It was replaced with the provider effect count taken before and after the call, which a
wrong implementation genuinely can move.

Conclusion: the rule earns its cost, and the class it catches is narrower and more specific than the
rule's wording suggests. The dangerous shape is not a hard-to-falsify property; it is an assertion
about **immutability of a value the language already makes immutable**, which reads exactly like a
real invariant check and is guaranteed green. It is worth naming that shape explicitly, because "did
X change?" is the natural way to evidence "this operation performs nothing", and in a codebase built
on immutable records it is almost always the wrong instrument — the right one is an observable
side-channel that a defect could actually disturb.

## Letting the runtime's shape settle a scope question, rather than choosing

Date: 2026-07-31
Trigger: an approach that worked and is not in `AGENTS.md`

Four consecutive integration slices had to decide the *scope* of an effect over a multi-member
activation, and each answer came from the shape of an existing runtime object rather than from a
preference: CM4 models one logical Release per attempt, so ordinary interaction opens for every
member or none (CBI12); one CM4 request carries the whole activation's binding exercises, so one
member's undeclared use condemns all of them (CBI16); a CM2 generation resolves every position at
once, so a declaration succession is one transaction (CBI17). In each case the alternative was a
defensible preference that would have had to be defended forever, and the argument that closed it
was a fact about a model already in the repository.

Conclusion: when a slice must decide whether an effect is per-member or per-whole, look first for an
existing model object whose cardinality already answers it, and record *which* object decided. This
is generalisable beyond these slices and is not currently written down anywhere. Two cautions worth
carrying with it: the reasoning is only honest when the object was not designed for this question, and
when two such objects agree the agreement should be recorded rather than relied on, since disagreement
would have forced a choice between them — CBI17's review says exactly this about CM2's generation and
CM4's restart scope.

## Falsifying a test by disabling a guard fights warnings-as-errors

Date: 2026-07-31
Trigger: an approach that worked and is not in `AGENTS.md`

The rule that each test must have been seen to fail once means deliberately breaking the
implementation and watching the right test go red. The obvious way to disable a guard — wrap it in
`if (false)` — does not compile here: warnings are errors repository-wide and the compiler reports the
body as unreachable. The same applies to commenting out a `return` that leaves a variable unused.

What works is a condition that is false at *runtime* but not statically: replacing `if (x.Length > 0)`
with `if (x.Length > 99)`, or `if not list.IsEmpty` with `if list.Length > 99`. The guard stays
reachable, the compiler stays quiet, and one character of diff distinguishes the broken build from the
real one — which also makes it obvious in `git diff` if a falsification is accidentally left behind.
Checking `git diff --numstat` shows insertions with zero deletions when the file is a pure addition,
which is a cheap way to confirm nothing was left behind.

Conclusion: the falsification rule needs a technique note, because the first thing a reader will try
is blocked by another rule in the same file. Worth adding: prefer a runtime-false condition over dead
code, and verify the revert rather than trusting it.

## The per-contract-item test rule earns its cost unevenly

Date: 2026-07-31
Trigger: a rule that cost real work, and a rule that caught something — the same rule, in different places

CBI18 was the first slice written under the rule that every capability-contract item gets its own
named test. Ten items across two independent stacks produced twenty named tests on top of the shared
vector suite, and roughly fifteen build-and-run cycles to see each one fail once. That is by far the
largest share of the slice's effort.

The value was not evenly distributed. Two items produced assertions nothing else would have: the one
stating that no declaration is consulted became a check on the entry point's *signature* — a pin that
the C# side broke at eight call sites and the F# side broke at compile time — and the one bounding the
slice's effects became a check that no member's portable stage moves, which the outcome-shaped vectors
do not look at. Both are claims about what the code does *not* do, which is precisely what a vector
inventory of outcomes cannot express. Other items were close to restatements of a vector that already
existed, and their named test added a second spelling of the same assertion.

Conclusion: the rule is worth keeping, but its value concentrates in contract items that assert an
*absence* — no parameter, no effect, no state change — because those are the ones a table of expected
outcomes structurally cannot carry. An item whose whole content is an expected outcome for a named
scenario is already pinned by its vector, and a named test for it duplicates rather than adds. Worth
saying so in the rule, so the effort lands where it pays.
