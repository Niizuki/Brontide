## "Take the highest-priority item" does not say whether blocked counts

Date: 2026-07-31
Trigger: a rule I could not apply without guessing what it meant

`AGENTS.md` says to inspect `docs/future/README.md` before beginning planned implementation work and
"take the highest-priority item unless the user directs otherwise". The highest-priority item is
Priority 1, Portable Component Binding, whose two remaining steps are fresh independent reviews and
owner question closure — both of which that document explicitly records as *not the implementer's to
close*. Taken literally the rule selects work an implementing agent cannot perform, and taken
loosely it selects nothing in particular.

The priority document does resolve it, but only in the first sentence of Priority 2, which says
Component Management is "the next implementable programme while Portable Binding awaits reviewer and
owner actions". So the answer exists and is one level of indirection away from the rule that sends
you looking.

Conclusion: a priority-order rule needs to say what it does about an item that is blocked on someone
other than the reader. Either the rule says "highest-priority item you can actually advance, and say
which one you skipped and why", or the priority document is required to mark blocked items so the
ordering is directly readable. The failure mode is quiet rather than loud — an agent picks the
implementable item, which is right, without ever recording that it departed from the literal
instruction.

## The "property that cannot fail" rule caught a vacuous assertion

Date: 2026-07-31
Trigger: a rule that caught something I can name

Writing CBI17's shared-vector test, I asserted that the admissions and grants in force were
identical before and after a succession, to evidence the contract's claim that succession performs
nothing. Re-reading the ground rule that a property which cannot fail is a review finding against
the property, I checked whether the assertion could fail, and it could not: both stacks hold those
values in immutable records, so no implementation of the operation could have moved them, in either
language. It was replaced with the provider effect count taken before and after the call, which a
wrong implementation genuinely can move.

Conclusion: the rule earns its cost, and the class it catches is narrower and more specific than the
rule's wording suggests. The dangerous shape is not a hard-to-falsify property; it is an assertion
about **immutability of a value the language already makes immutable**, which reads exactly like a
real invariant check and is guaranteed green. It is worth naming that shape explicitly, because "did
X change?" is the natural way to evidence "this operation performs nothing", and in a codebase built
on immutable records it is almost always the wrong instrument — the right one is an observable
side-channel that a defect could actually disturb.

## Letting the runtime's shape settle a scope question, rather than choosing

Date: 2026-07-31
Trigger: an approach that worked and is not in `AGENTS.md`

Four consecutive integration slices had to decide the *scope* of an effect over a multi-member
activation, and each answer came from the shape of an existing runtime object rather than from a
preference: CM4 models one logical Release per attempt, so ordinary interaction opens for every
member or none (CBI12); one CM4 request carries the whole activation's binding exercises, so one
member's undeclared use condemns all of them (CBI16); a CM2 generation resolves every position at
once, so a declaration succession is one transaction (CBI17). In each case the alternative was a
defensible preference that would have had to be defended forever, and the argument that closed it
was a fact about a model already in the repository.

Conclusion: when a slice must decide whether an effect is per-member or per-whole, look first for an
existing model object whose cardinality already answers it, and record *which* object decided. This
is generalisable beyond these slices and is not currently written down anywhere. Two cautions worth
carrying with it: the reasoning is only honest when the object was not designed for this question, and
when two such objects agree the agreement should be recorded rather than relied on, since disagreement
would have forced a choice between them — CBI17's review says exactly this about CM2's generation and
CM4's restart scope.

## Falsifying a test by disabling a guard fights warnings-as-errors

Date: 2026-07-31
Trigger: an approach that worked and is not in `AGENTS.md`

The rule that each test must have been seen to fail once means deliberately breaking the
implementation and watching the right test go red. The obvious way to disable a guard — wrap it in
`if (false)` — does not compile here: warnings are errors repository-wide and the compiler reports the
body as unreachable. The same applies to commenting out a `return` that leaves a variable unused.

What works is a condition that is false at *runtime* but not statically: replacing `if (x.Length > 0)`
with `if (x.Length > 99)`, or `if not list.IsEmpty` with `if list.Length > 99`. The guard stays
reachable, the compiler stays quiet, and one character of diff distinguishes the broken build from the
real one — which also makes it obvious in `git diff` if a falsification is accidentally left behind.
Checking `git diff --numstat` shows insertions with zero deletions when the file is a pure addition,
which is a cheap way to confirm nothing was left behind.

Conclusion: the falsification rule needs a technique note, because the first thing a reader will try
is blocked by another rule in the same file. Worth adding: prefer a runtime-false condition over dead
code, and verify the revert rather than trusting it.

## The per-contract-item test rule earns its cost unevenly

Date: 2026-07-31
Trigger: a rule that cost real work, and a rule that caught something — the same rule, in different places

CBI18 was the first slice written under the rule that every capability-contract item gets its own
named test. Ten items across two independent stacks produced twenty named tests on top of the shared
vector suite, and roughly fifteen build-and-run cycles to see each one fail once. That is by far the
largest share of the slice's effort.

The value was not evenly distributed. Two items produced assertions nothing else would have: the one
stating that no declaration is consulted became a check on the entry point's *signature* — a pin that
the C# side broke at eight call sites and the F# side broke at compile time — and the one bounding the
slice's effects became a check that no member's portable stage moves, which the outcome-shaped vectors
do not look at. Both are claims about what the code does *not* do, which is precisely what a vector
inventory of outcomes cannot express. Other items were close to restatements of a vector that already
existed, and their named test added a second spelling of the same assertion.

Conclusion: the rule is worth keeping, but its value concentrates in contract items that assert an
*absence* — no parameter, no effect, no state change — because those are the ones a table of expected
outcomes structurally cannot carry. An item whose whole content is an expected outcome for a named
scenario is already pinned by its vector, and a named test for it duplicates rather than adds. Worth
saying so in the rule, so the effort lands where it pays.

## Delivering conformance evidence and preserving a closed review pull against each other

Date: 2026-07-31
Trigger: two rules that pointed different ways

Implementing a requirement from the current architecture target and recording it is one task, and it
cannot be completed by one actor. Recording delivered evidence means flipping the requirement's
status in each stack's conformance matrix. The status registry pins each matrix's hash, so the
registry must change too. The closed independent-review request pins the *registry's* hash, and that
directory's README states the consequence plainly: any change to a pinned source invalidates the
request. The verifier then demands attestations whose target commit matches, and `AGENTS.md` requires
those attestations to come from a reviewer that is not an implementation actor.

So an implementing agent can produce the implementation, the tests, and the contract, and cannot
produce the record that says so. Every step is individually correct; together they mean the matrices
permanently understate what is delivered until someone else acts.

Conclusion: a repository that pins its own status registry inside a closed review has made "record
that a requirement is now met" a two-party operation, and nothing in the instructions says so at the
point where an agent is told to deliver a requirement. The instruction to take the highest-priority
item should say that delivering a conformance requirement ends in a handoff rather than in a green
matrix, or the pin chain should be arranged so that evidence status can move without disturbing a
closed review. Either is fine; the current silence guarantees an agent discovers it only after doing
the work, at the gate.

## A declared limit that nothing checked, found by reading a predecessor's contract as a test case

Date: 2026-07-31
Trigger: a rule that caught something you can name

A new integration slice was being built directly on the one before it. `AGENTS.md` says a comment
claiming behaviour under a named scenario is a test case, and that a load-bearing assertion — a claim
some other decision rests on — is one as well. Applying those to the *predecessor's* capability
contract rather than to the code being written turned up two claims that neither a test nor the
implementation checked: that its input was one entry per member of the successor generation, and that
it added or removed no position. A caller could hand it a strict subset of the positions the successor
generation resolved, together with a plan built from that same subset, and get a cutover to a
generation covering fewer members than resolution had produced — the omitted member retired, and no
refusal anywhere. Both independent stacks behaved identically. The pin was written before the fix and
failed by reporting success and cutting over, which is what confirmed the diagnosis rather than the
guess about it.

The two "a claim is a test case" rules pay off when they are applied to the contract of the slice
being *built on*, not only to the one being written. A completed slice's stated limits are the
cheapest place in the repository to look for an unchecked claim, because that slice's own vectors are
typically derived from a single declaration which satisfies its limits by construction and therefore
cannot test them. Worth treating as a standing step whenever a new consumer is pointed at an existing
seam, rather than as something a completeness review at the time would have caught — that review ran,
and did not.

## Where a correction to a completed slice gets recorded is not stated

Date: 2026-07-31
Trigger: a rule you could not apply without guessing what it meant

The defect above was in a slice whose capability contract and contract-completeness review are dated,
completed artifacts. `AGENTS.md` requires a found defect to be pinned and fixed, and requires
documentation to be updated in the same change when a change alters a claimed milestone or known
limitation. It also warns against rewriting documents that carry evidence pins, and the
implementation plans put dated rulings in a resolved-questions section rather than annotating
decisions in place. None of that says whether the older slice's contract should now record that a
limit it declared is enforced, or whether the correction belongs only in the new slice's artifacts.
Guessed: left the earlier contract and review untouched, and recorded the finding in the new slice's
completeness review, both stacks' changelogs under a `Fixed` heading, and the future-work index.

A sentence somewhere on this would remove the guess: when a defect is found in a completed slice
while building its successor, the correction is recorded in the successor's artifacts and the
changelogs, and the completed slice's dated contract and review are left as the record of what was
believed at the time. Any of the plausible answers is fine — the cost is that the next agent has to
re-derive one, and two agents choosing differently leaves the repository inconsistent about where its
corrections live.

## "Released no member" is a vacuous way to evidence a release barrier here

Date: 2026-08-01
Trigger: a rule that caught something you can name

A release-barrier test asserted that an activation whose added member never reports Ready releases
none of its members, and it passed. Applying `AGENTS.md`'s "you must have seen each test fail once"
by breaking the barrier — releasing each member as it reported Ready instead of at the barrier —
showed the assertion still green, because the failure path retires every member it established and a
retired member is not released either. The assertion was insensitive to the exact defect it named,
and was replaced with an ordinary Operation attempted on the surviving member, which a wrong
implementation answers and a correct one refuses.

Reading the test would not have found this. The assertion is a direct statement of the property and
nothing about it looks weak; what makes it vacuous is a detail of the cleanup path several call
frames away. The shape is worth naming because it recurs: in this codebase a failed activation
retires what it established, so **any assertion of the form "the failed attempt released nobody" is
satisfied by both the right implementation and a wrong one**, and the instrument that separates them
is an attempted interaction rather than a state count. The rule that pays for itself here is the
mechanical half — break it and watch — not the intention behind it.

## Two sessions implemented the same item, and the duplicate is what the priority document invites

Date: 2026-08-01
Trigger: a rule that cost real work for no benefit visible here

`AGENTS.md` says to inspect `docs/future/README.md` and take the highest-priority item. Two sessions
did exactly that against the same tree state and both built CBI20, independently and to the same
conclusions, one landing while the other was in review. The whole second implementation was
discarded. Nothing in the instructions is wrong in isolation: the priority document names the next
item, and an agent is told to take it.

What is missing is any signal that an item is already being worked. The document records what is
*done* and what is *next*, and a branch or an open pull request is the only evidence that the next
item is in flight — which the rule never sends anyone to look at. One sentence would remove most of
the cost: before starting the named item, check for a branch or open pull request against it, and say
so if one exists. The near-miss is invisible from inside either session, which is why it is being
recorded from outside one.

Worth keeping from the collision: the two implementations agreed on every substantive answer except
one. A receiving-domain Actor that a *dropped* participant held may be taken by a different party in
an added member — permitted by the merged slice, because CBI13's mapping rule is a property of an
activation and the retained one ends at cutover; refused by the discarded one, because the two
generations are both established between Release and retirement, so the conflation would briefly be
live. That is a real fork in the reasoning that only a duplicate exposed, and it is the kind of thing
independent implementation is supposed to produce.
