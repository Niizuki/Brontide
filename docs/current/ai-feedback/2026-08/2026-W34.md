# 2026-W34 agent feedback

## Writing the check first said the class was wider than the finding's own story

Date: 2026-08-20
Trigger: 4 — a rule that caught something you can name

The task was to bring one more fact under the Channel 0.2 owned-fact mechanism: a record published in
several design artifacts and, until now, watched by a hand-written sweep in the design verifier. The
rule in `AGENTS.md` says to write the check before the correction and confirm it fails *for the reason
claimed*. Left to itself this looked like a step worth skipping — the surfaces were already known, and
the retained finding that motivated the work names them.

They were not already known. The finding's account is about two cells of one table, and every document
in the package restates it that way. Run before any surface was converted, the new check reported
**three**: the two cells and a transition row in a different artifact, which had the same shape and
which no cycle had mentioned. Had the correction been written first and the check after, the check
would have been green on arrival and the third surface would have been converted only by luck, or not
at all.

The conclusion is narrower than "write tests first" and worth stating on its own: **when the work is
to generalise a guard, run the new guard against the unchanged repository before changing anything,
and count what it finds.** A guard built from a defect report inherits that report's inventory of
where the defect was; running it before the fix is the only cheap way to learn whether that inventory
was complete. The count is the evidence, and it belongs in the change's own record — a later reader
otherwise has no way to tell a guard that found three instances from one written over three known
ones.

## A generator's non-semantic output is unreviewed surface

Date: 2026-08-20
Trigger: 5 — an approach that worked, is not in `AGENTS.md`, and would generalise

Documentation rules here cover what a document says, and the gates check it thoroughly. This
repository now also has a *generator*: one declaration owns certain facts and a script renders them
into every artifact that publishes them, so for those regions the script is the only writer. Nothing
in the rules or the gates covers what such a script does to the bytes it was not asked to change.

Using it exposed three such changes at once. The rewrite added a byte-order mark to artifacts that had
none, because the obvious Windows PowerShell way to write a file adds one unconditionally; it emitted
CRLF into files stored with LF; and, because it rewrote every rendered region in any file it touched,
it re-wrapped regions belonging to facts the run was not about, putting unrelated sites into the diff.
All three were invisible to every check in the package — they are not what any fact declares — and all
three were visible immediately in `git diff`.

The approach, which is cheap and would generalise to any generator: **after a generator's first run on
real files, read its whole diff and ask which changes nothing requested.** Then make the tool
byte-faithful to everything outside its own regions — preserve the file's encoding and line endings,
and rewrite only the regions that actually disagree with the declaration. A generator that touches a
document's presentation as a side effect makes every future diff harder to read, in a package whose
only real detector is a person reading it.

## A guard's comment is a claim, and testing it against the code found two live defects

Date: 2026-08-20
Trigger: a rule that caught something you can name

`AGENTS.md` says to pin a found defect with a failing test before fixing it, and to have seen each
test fail once. Applied to *guards* rather than to product code, that turns into a question nobody
had asked here: does this check ask the question its own comment says it asks?

Two of six findings in one pass came from that question and neither was reachable by reading. A
status-block check's comment said "the pointer must RESOLVE" and the code looked the destination up
by the artifact's file name, never reading the anchor written in the pointer; renaming the heading it
pointed at left every pointer dead and the whole gate green. A pin check's comment described "the
design artifacts" and its list held eight of nine, so a commit touching only the omitted one passed.
Both checks had been green since they were written, and both were written to close an earlier
instance of the class they were now missing.

The conclusion is one sentence: **a comment on a guard is a claim about that guard, and the cheap
test is to break the thing the comment says is caught.** It is the same rule the repository already
has for comments claiming behaviour under a named scenario, pointed at verification code instead of
at product code, and it costs one mutation per guard.

## A probe harness must restore from a snapshot it took, never from git

Date: 2026-08-20
Trigger: an approach that worked, is not in `AGENTS.md`, and would generalise

The productive method for checking a guard is mechanical: mutate a file so the defect the guard
names is present, run the gate, assert it fails, restore. Twenty-odd of those in one pass reproduced
every probe an earlier pass had recorded and confirmed four new ones.

The trap is in the last step. The obvious restore is `git checkout -- <path>`, and it silently
discarded an hour of uncommitted corrections the moment a probe ran against a file the same session
had edited — including on the setup-failure path, where the probe never ran at all. Nothing warned:
the harness reported a setup failure and the working tree quietly went back to `HEAD`.

Two rules, either of which is sufficient and both of which are cheap: **restore from bytes read
before the mutation**, so the harness can only undo its own edit; and **run probes against a
committed tree**, so a mistake costs nothing. This matters more here than in most repositories
because the gates are the deliverable, so probing them is ordinary work rather than an occasional
exercise.

## Testing a guard's comment against its code found a property that could not stay green

Date: 2026-08-20
Trigger: a rule that caught something you can name

`AGENTS.md` requires a property to be able to fail and, since the AE1 correction here, to be able to
stay green: a property red on conforming behaviour is the same defect from the other end. The rule
says nothing about the *guards* that keep such a property honest, and those are where the last three
defects have been.

The method that found this one is one sentence: **read each guard's comment as a claim about the
guard, and break the thing the comment says is caught.** A cross-check's comment promised that the
artifact declares no transition its copy of the table lacks. The artifact's table had ten rows, two
of which name a class of states rather than one state, and the reader required a single state -- so
it compared eight against eight and reported them identical. Two capability properties were
consequently red on a session that faults, which the design explicitly permits from any nonterminal
state.

The generalisation is not "write better regexes". It is that a recognizer which cannot read a row
must **fail on that row rather than skip it**. Four corrections in this package have now had the same
shape and the same answer: a permit list for undeclared front matter, resolution for a pointer, one
derived list for an artifact set, and a parser that throws on an unrecognised table cell. A guard that
silently drops what it cannot read certifies its own completeness.

## Keep the probes, not just the findings

Date: 2026-08-20
Trigger: an approach that worked, is not in `AGENTS.md`, and would generalise

`AGENTS.md` says a defect is pinned with a failing test before it is fixed, and that the test outlives
the fix as the regression guard. That is stated for product code. Applied to verification code the
rule has a gap nobody had noticed: the "test" for a guard is a mutation of the working tree, and three
successive review passes here wrote those mutations, ran them, described them in prose, and threw them
away. The next pass rebuilt them from the prose.

Four of them had silently stopped applying -- the text they anchored on had been corrected a cycle
earlier -- so "the guards fire" was a claim in two retained records that nothing was checking. The fix
was to keep the corpus as data and run it in the gate, with one rule that matters more than the rest:
a probe whose anchor no longer occurs **fails**, because a probe that cannot be applied has stopped
measuring and looks exactly like one that passed.

The conclusion generalises to any repository whose deliverable includes its own checks: **a guard with
no probe is unmeasured, and a probe that lives only in prose is a probe that has already rotted.**
