## Test the wrapper, not only the classified dependency

Date: 2026-08-03
Trigger: a rule caught something you can name

While adding the first real-process activation at the Component Management/Portable Binding
composition root, the requirement to write and read a failing test before changing behavior exposed
a classification defect in only one stack. Portable Binding already classified process loss, and its
parity suites passed, but the Reference composition wrapper caught the declared process exception
under its generic fallback and returned `portable-interconnection-failed`; Minimal preserved
`portable-process-interrupted`.

When a higher-level integration claims a dependency's failure taxonomy, put the failing vector
through that integration boundary even if the dependency already has complete parity evidence. A
wrapper's exception/result projection is a separate semantic decision and lower-layer tests cannot
pin it.

## Making a "happens before" claim able to fail

Date: 2026-08-03
Trigger: 5 — an approach that worked, is not in `AGENTS.md`, and would generalise

A capability contract stated that a recovery floor is handed to the host only *after* the checkpoint
it describes is durable. Every other claim in that slice is a value — an outcome code, an attempt
count, a gap sequence — and a value is compared once the work is over. An ordering claim has nothing
to compare that way: both orders leave the same end state, so an assertion written after the sequence
passes under either one. The rule that each `C1`-`Cn` item gets a named test says nothing about how to
write one that can fail, and the obvious draft here would have been exactly the tautology the
"you must have seen each test fail once" rule exists to catch — the durable write happens inside the
same call that produces the floor, so by the end it is always there.

What worked was moving the assertion inside the sequence instead of after it. The test double for the
*later* step re-derived the earlier step's durable effect at the moment it was invoked, and recorded
whether it was present. Denying it that effect — pointing the re-derivation at a path nothing had
written — made it record the negative, which is how the assertion was shown to be live rather than
decorative.

Conclusion: when a contract says A happens before B, assert it by having the test double for B read
A's durable effect at the moment B runs, and prove the assertion live by denying it that effect. An
ordering check written after both have happened is a check on the end state, which is identical under
either order, and it will pass over the exact defect it was written for.

## Three corruption tests, none of which tested the check

Date: 2026-08-03
Trigger: 4 — a rule caught something I can name

A durable record was given a trailing SHA-256 integrity tag, and three vectors were written against
it: a flipped version marker, a truncated file, and a file with one trailing byte. All three passed.
Under the rule that every test must be seen failing once, the tag comparison was then disabled
deliberately — and all three still passed. Every one of them was refused by structural parsing
*before* the tag was ever consulted: the flipped marker failed the version string, and the truncation
and the extra byte shifted the record so the remaining structure did not terminate cleanly. The
integrity check was, at that point, unreachable by any test, with three green cases appearing to
cover it.

The repair was a fourth vector altering a byte the parser accepts — one byte of the sequence field,
which yields a different but entirely well-formed record — so nothing except the tag can refuse it.
With the check disabled that vector fails; with it restored, it passes.

Conclusion: tests for a *detector* drift toward inputs that some earlier layer rejects first, and
they then go green for a reason that has nothing to do with the detector. Whenever a check exists to
catch corrupted-but-plausible data, at least one case must be corrupt in a way every earlier layer
accepts — and the only dependable way to find out that the existing cases are not is to disable the
check and watch them stay green.

## Build the design you rejected, and count the vectors that cannot tell it apart

Date: 2026-08-04
Trigger: an approach that worked, is not in `AGENTS.md`, and would generalise

`AGENTS.md` requires that every test has been seen to fail once, either by writing it before the code
path or by breaking the implementation deliberately. Both forms answer the same question — is this
assertion wired to anything — and a random break answers it. Implementing a slice whose whole content
was a choice between two readings of one word turned up a second question the rule does not reach.

The slice makes a launch re-check a publisher's trust policy after acquisition. "Revalidate" has two
plausible readings: re-take the decision against whatever policy is now in force, or check that the
policy has not moved since the one that authorized acquisition. The second is the more literal
reading and is wrong — a host that polls receives updates about other publishers constantly, and
that reading refuses every one of them. Rather than only breaking the chosen design, the rejected
design was implemented and the vector set run against it. **Five of six vectors passed**, including
both vectors written specifically for a revoked publisher. One vector separated them: a policy update
that revokes a *different* publisher. Under the rejected reading it refuses; under the chosen one it
launches.

The number is the useful part. A rejected design that passes every vector means the vector set does
not state the choice that was made, so two independent implementations reading the same contract will
agree by accident and the disagreement will surface later as a defect in both. Breaking the chosen
implementation cannot detect this, because the assertions are wired and go red exactly as intended;
what is missing is a case, not a wire.

The generalisable practice: whenever a slice's substance is a choice between two readings of the same
requirement, implement the reading that was rejected and run the vectors against it before writing
the contract. Report how many vectors failed to distinguish the two. If the answer is "all of them",
the contract is silent about its own central decision and needs a vector, not better prose.

## Boundary-value tests must include representability

Date: 2026-08-05
Trigger: a rule caught something you can name

While implementing a bounded time policy, the capability tests covered zero, maximum duration,
deadline equality, and monotonic expiry. Applying the rule to pin each behavior as it was written
prompted one additional concrete boundary: a valid injected `DateTimeOffset` near the representable
maximum. Both implementations threw while adding the bounded grace interval instead of returning the
contract's fail-closed invalid-observation result.

For policies that derive an instant by adding a bounded duration, the named boundary cases should
include arithmetic representability as well as semantic minimum and maximum values; otherwise a
fully bounded duration can still escape the declared result model at the clock type's edge.

## A named persistence contract exposed a false successful write

Date: 2026-08-05
Trigger: a rule caught something you can name

CBI54's Minimal implementation accepted and integrity-tagged a durable ownership record, but its
first close-and-reopen test reported the record as corrupt: reflection-based JSON serialization of
the private F# record wrote bytes that the same type could not reconstruct. The C1-C8 rule made the

cross-process ownership claim was finalized.

For durable state, keep a named write-close-open assertion at the capability boundary and prefer an
explicit wire encoding over reflection across private language-specific representations.

## Process-test setup must not leak into ordinary evidence

Date: 2026-08-05
Trigger: a rule caught something you can name

The final repository gate reruns cross-process tests only after publishing provider paths, while the
ordinary solution test run intentionally has no such environment. New CBI55 non-process tests used
the provider path merely to derive an executable filename. Several were therefore skipped in the
ordinary run, and two acquired an operating-system ownership lock before the missing environment
raised the skip, leaving cleanup unable to remove their temporary directory. The full-gate rule
caught behavior that the focused process-enabled run had hidden.

Any test fact that does not require a live process must be constructed without live-process
configuration. In mixed suites, acquire external resources only after every optional environment
dependency has been resolved, so a skip cannot strand a lock or partially execute setup.

## The seen-it-fail rule caught a rotation test that asserted nothing

Date: 2026-08-05
Trigger: a rule that caught something you can name

A slice added key rotation to a durable registry that also holds a policy snapshot. One capability
claimed the rotation is not a trust event, and the obvious test captured the snapshot before the
rotation, applied the rotation, and asserted the snapshot was unchanged. It passed. It could not have
done anything else: the rotation does not touch that field, so both sides of the comparison were the
same object, and a wrong implementation that moved the field on the *next* write would still have
been green. Only the `AGENTS.md` requirement to watch each test fail once exposed it — deliberately
making the rotation move the field left the test passing, which is what a tautology looks like from
the outside. The replacement asserts the value written *after* the rotation, and it goes red under the
same break.

The generalisable part is the smell rather than the rule: a test asserting that an operation left
something unchanged is worth suspecting whenever the operation never writes that thing, because the
assertion then holds by construction rather than by behaviour. What makes such a test real is
asserting the unchanged property across the *next* operation that does write it.

## An ordered chain of guards makes "which refusal fires" the claim most worth asserting first

Date: 2026-08-06
Trigger: a rule that caught something I can name

A slice added a durable guard whose retention path checks several conditions in order, and a
truncation test that expected a chained record to be refused for a particular reason. Following the
rule that a capability item's assertions are written with the code rather than after it, both
expectations were written as executable assertions before the contract prose was drafted. Both were
wrong, and in the same way: the refusal happened, but under a different code than the one claimed.
Offering a floor at generation zero to a store already past zero is refused as a regression rather
than as a pin mismatch, because the pin check only fires when the named authority differs and the
ordinal comparison is what catches everything else. A policy update signed by an authority a
truncated chain no longer has in force is refused as an authority mismatch rather than as an invalid
signature, because identity is compared before the signature is verified.

Neither error was visible by inspection. The implementation is correct under either reading — the
input is refused, no effect occurs, nothing leaks — and only the reported code differs, so reviewing
the code answers the wrong question. Both claims were on their way into a capability contract as
prose that a later implementer would have read as normative, and a later reader diffing behaviour
against that prose would have found a divergence that was never there.

The conclusion is a fourth thing to write a test *for*, alongside the three the rules already name.
Where a decision is a chain of guards, **any claim about which guard fires is a test case**, and it
is the class where writing the assertion first pays most, because the property that makes the code
correct — something refuses this — is exactly the property that hides the error. Stating the code in
a document without having run it is the same mistake in the direction that survives review.

## A class-guard needs an enumerable class, which usually means moving the vocabulary first

Date: 2026-08-07
Trigger: an approach that worked, is not in AGENTS.md, and would generalise

A slice added two result codes. A later slice validated results against a hand-written list of the
codes that existed when it was written, so the two new ones were refused and the run was recorded as
an interruption that had not happened. Neither slice's tests could see it: the producing suite never
composed with the validator, and the validating suite never produced a new code.

The rules already say to pin the class rather than the instance — a guard that fails when the next
member is added and left out beats assertions naming today's members. What they do not say is that
this is often impossible as the code stands, and what to do about it. The members here were string
literals scattered across several producers, so there was no "class" to enumerate and no guard to
write; the only available repair was adding the two missing strings, which fixes this instance and
leaves the next one exactly as reachable.

What worked was to make the class enumerable before writing the guard: move the vocabulary into one
place, have the producers use it instead of literals, have the validator ask it rather than restate
it, and write the test as a walk over it. The guard then fails on the next addition for a structural
reason rather than because someone remembered. The move is small and mechanical, and it is the step
that turns "pin the class" from advice into something that can actually be done.

The conclusion for a reader with no context: when a guard ought to cover a class and the class is a
set of literals spread across producers, treat extracting the shared vocabulary as part of writing
the guard rather than as a refactor to do first or skip. If the members cannot be enumerated at a
single point, the class cannot be pinned, and any test written instead is naming today's members
while looking like it is doing more.

## A "next boundary" sentence is a hypothesis, and reading it as a specification builds the wrong thing

Date: 2026-08-07
Trigger: an approach that worked, is not in AGENTS.md, and would generalise

Each slice in this programme ends by naming the next bounded boundary, and the next slice starts from
that sentence. Three consecutive slices found the sentence wrong in the same way, and each time the
correction was the slice's main result rather than an obstacle to it.

One said a forward-referenced operation would handle a case; reading the model to implement it showed
the model has no such operation, and the deferring slices had already been correct. One said a
durable record must note which of two sub-operations had run; writing that note turns out to be
strictly worse than not writing it, because the note cannot be atomic with the effect it describes
while the effect already records itself. One said evidence must name which of two things the host had
verified; the host should be asserting about neither, because both verify themselves, and the right
change was to make the evidence narrower rather than wider.

The common shape is that a boundary sentence is written at the end of slice N, from the shape slice N
happens to have, and it tends to propose a symmetry the models do not actually have. It reads as a
specification because it is phrased as one — "the journal must record", "the evidence must name" —
so an implementer who follows the letter produces something defensible and wrong, and only an
implementer who re-derives it from the models finds out.

What worked was to treat the sentence as a hypothesis with a first task attached: before building
what it describes, check whether the models can represent it and whether a cheaper arrangement gets
the same guarantee. That check cost little each time and produced the finding each time. The
generalisable form for a reader with no context: when a planning note tells the next change what to
build, phrase it as the question that change must answer rather than the answer, and treat an
inherited answer as something to falsify before implementing.
