## Test the wrapper, not only the classified dependency

Date: 2026-08-03
Trigger: a rule caught something you can name

While adding the first real-process activation at the Component Management/Portable Binding
composition root, the requirement to write and read a failing test before changing behavior exposed
a classification defect in only one stack. Portable Binding already classified process loss, and its
parity suites passed, but the Reference composition wrapper caught the declared process exception
under its generic fallback and returned `portable-interconnection-failed`; Minimal preserved
`portable-process-interrupted`.

When a higher-level integration claims a dependency's failure taxonomy, put the failing vector
through that integration boundary even if the dependency already has complete parity evidence. A
wrapper's exception/result projection is a separate semantic decision and lower-layer tests cannot
pin it.

## Making a "happens before" claim able to fail

Date: 2026-08-03
Trigger: 5 — an approach that worked, is not in `AGENTS.md`, and would generalise

A capability contract stated that a recovery floor is handed to the host only *after* the checkpoint
it describes is durable. Every other claim in that slice is a value — an outcome code, an attempt
count, a gap sequence — and a value is compared once the work is over. An ordering claim has nothing
to compare that way: both orders leave the same end state, so an assertion written after the sequence
passes under either one. The rule that each `C1`-`Cn` item gets a named test says nothing about how to
write one that can fail, and the obvious draft here would have been exactly the tautology the
"you must have seen each test fail once" rule exists to catch — the durable write happens inside the
same call that produces the floor, so by the end it is always there.

What worked was moving the assertion inside the sequence instead of after it. The test double for the
*later* step re-derived the earlier step's durable effect at the moment it was invoked, and recorded
whether it was present. Denying it that effect — pointing the re-derivation at a path nothing had
written — made it record the negative, which is how the assertion was shown to be live rather than
decorative.

Conclusion: when a contract says A happens before B, assert it by having the test double for B read
A's durable effect at the moment B runs, and prove the assertion live by denying it that effect. An
ordering check written after both have happened is a check on the end state, which is identical under
either order, and it will pass over the exact defect it was written for.

## Three corruption tests, none of which tested the check

Date: 2026-08-03
Trigger: 4 — a rule caught something I can name

A durable record was given a trailing SHA-256 integrity tag, and three vectors were written against
it: a flipped version marker, a truncated file, and a file with one trailing byte. All three passed.
Under the rule that every test must be seen failing once, the tag comparison was then disabled
deliberately — and all three still passed. Every one of them was refused by structural parsing
*before* the tag was ever consulted: the flipped marker failed the version string, and the truncation
and the extra byte shifted the record so the remaining structure did not terminate cleanly. The
integrity check was, at that point, unreachable by any test, with three green cases appearing to
cover it.

The repair was a fourth vector altering a byte the parser accepts — one byte of the sequence field,
which yields a different but entirely well-formed record — so nothing except the tag can refuse it.
With the check disabled that vector fails; with it restored, it passes.

Conclusion: tests for a *detector* drift toward inputs that some earlier layer rejects first, and
they then go green for a reason that has nothing to do with the detector. Whenever a check exists to
catch corrupted-but-plausible data, at least one case must be corrupt in a way every earlier layer
accepts — and the only dependable way to find out that the existing cases are not is to disable the
check and watch them stay green.

## Build the design you rejected, and count the vectors that cannot tell it apart

Date: 2026-08-04
Trigger: an approach that worked, is not in `AGENTS.md`, and would generalise

`AGENTS.md` requires that every test has been seen to fail once, either by writing it before the code
path or by breaking the implementation deliberately. Both forms answer the same question — is this
assertion wired to anything — and a random break answers it. Implementing a slice whose whole content
was a choice between two readings of one word turned up a second question the rule does not reach.

The slice makes a launch re-check a publisher's trust policy after acquisition. "Revalidate" has two
plausible readings: re-take the decision against whatever policy is now in force, or check that the
policy has not moved since the one that authorized acquisition. The second is the more literal
reading and is wrong — a host that polls receives updates about other publishers constantly, and
that reading refuses every one of them. Rather than only breaking the chosen design, the rejected
design was implemented and the vector set run against it. **Five of six vectors passed**, including
both vectors written specifically for a revoked publisher. One vector separated them: a policy update
that revokes a *different* publisher. Under the rejected reading it refuses; under the chosen one it
launches.

The number is the useful part. A rejected design that passes every vector means the vector set does
not state the choice that was made, so two independent implementations reading the same contract will
agree by accident and the disagreement will surface later as a defect in both. Breaking the chosen
implementation cannot detect this, because the assertions are wired and go red exactly as intended;
what is missing is a case, not a wire.

The generalisable practice: whenever a slice's substance is a choice between two readings of the same
requirement, implement the reading that was rejected and run the vectors against it before writing
the contract. Report how many vectors failed to distinguish the two. If the answer is "all of them",
the contract is silent about its own central decision and needs a vector, not better prose.

## Boundary-value tests must include representability

Date: 2026-08-05
Trigger: a rule caught something you can name

While implementing a bounded time policy, the capability tests covered zero, maximum duration,
deadline equality, and monotonic expiry. Applying the rule to pin each behavior as it was written
prompted one additional concrete boundary: a valid injected `DateTimeOffset` near the representable
maximum. Both implementations threw while adding the bounded grace interval instead of returning the
contract's fail-closed invalid-observation result.

For policies that derive an instant by adding a bounded duration, the named boundary cases should
include arithmetic representability as well as semantic minimum and maximum values; otherwise a
fully bounded duration can still escape the declared result model at the clock type's edge.

## A named persistence contract exposed a false successful write

Date: 2026-08-05
Trigger: a rule caught something you can name

CBI54's Minimal implementation accepted and integrity-tagged a durable ownership record, but its
first close-and-reopen test reported the record as corrupt: reflection-based JSON serialization of
the private F# record wrote bytes that the same type could not reconstruct. The C1-C8 rule made the
lineage round trip a named assertion in the feature change, so the failure appeared before the
cross-process ownership claim was finalized.

For durable state, keep a named write-close-open assertion at the capability boundary and prefer an
explicit wire encoding over reflection across private language-specific representations.
